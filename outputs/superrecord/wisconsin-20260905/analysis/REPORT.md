# Wisconsin 分阶段性能分析

口径：32 B entry，固定原生二进制；100次测量（Cuckoo/TreePIR/Flat为16次），均有3次预热。单位ms，吞吐量用逻辑档位容量除以平均服务器耗时。数据来自已完成的JSON及exit0进程记录；本次没有重跑或修改C++计时。

## h3 为什么比 h1 快

h=3合并的是**同一层内三个相邻entry**，并非三个树层。h1的G8/P3给一个256-bit entry分配288bit，槽位利用率88.89%；h3的G64/P1或G32/P2给三个entry分配768bit，利用率100%。理想容量下降11.11%，考虑h3矩阵padding后，实际扫描量下降约8.33%。

- 1gb: h3耗时减少 **16.053%**；吞吐提升 **19.123%**。配对block bootstrap 95%加速比区间 **1.18969–1.19243**（10000次重采样）。
- 4gb: h3耗时减少 **9.030%**；吞吐提升 **9.927%**。配对block bootstrap 95%加速比区间 **1.09777–1.10050**（10000次重采样）。

1GiB中，旋转/投影合计节省115.658ms，扫描节省81.855ms，查询前端节省39.992ms；折叠和恢复多花57.237ms。4GiB中扫描节省426.648ms是主要收益，但折叠和恢复多花230.055ms，抵消了部分收益。

扫描时间下降并不完全等同于扫描字节下降：N0与矩阵形状同时改变，观测到有效扫描带宽也不同；本次未用硬件计数器隔离缓存/频率因素，不能把全部差值归因于容量。

## 计时代码与新增产物

本轮使用既有src/tests/test_tree_superrecord_benchmark.cpp、src/merkle_benchmark.cpp相关计时、Cuckoo与TreePIR adapter的结构化输出；未增加C++ instrumentation。新增scripts/analyze_wisconsin_profiles.py负责校验、统计和归一化，scripts/plot_wisconsin_profiles.R负责独立图表。CSV/JSON保留未四舍五入数据。

后续如要把N0形状影响与容量收益严格分离，需要固定布局的内核消融；当前报告只对已有实测作归因，不增补未经运行的硬件指标。
